#+TITLE: The browser's side: memory and CPU

What pad costs the browser that opens it, measured on 2026-10-11, 12 and 14, against two references: a bare page with a plain =<textarea>= holding the same text (the floor: what Chromium itself needs to show it), and other sites, light and ordinary, loaded the same way. Goal (AUDIT.org section 17): the least memory and CPU the features allow, on desktop and on phones.

* How it's measured
+ The graphs are drawn from the raw results by =scripts/bench/client/graphs.ts=.
+ Chromium 153 (Arch package; 154 on 2026-10-14), headless unless a table says otherwise, on the author's desktop. "Mobile" is Chromium's emulation: a Pixel 7's viewport and user agent, touch, the CPU slowed 4×. It is not Android: a phone's memory pressure, which makes the collector run sooner, isn't reproduced.
+ Memory is PSS (each process's private pages plus its share of shared ones), read from =/proc/<pid>/smaps_rollup=, summed over Chromium's processes of a kind (the renderers, which run the page; the GPU process; the browser process). "Above blank" is minus the same profile's renderers on =about:blank=, measured first in each run.
+ "At rest": 1.5 s after the action, two forced garbage collections, then read. What a tab keeps while you look at it.
+ "Peak": the highest of the renderers' PSS, sampled from the action's start (a submit, a click, the first key) until its result shows: every 20 ms by =drive.ts= since 2026-10-14, every 100 ms before (a claim, over in ~80 ms, could fall between two samples); every 100 ms by =cpu.ts= and =costs.ts=, 50 ms by =export-pss.ts=. The peaks before 2026-10-14 are the max of one to a few samples.
+ Each run is a fresh profile. One run per cell unless the table says otherwise: differences under ~10 MiB are within noise.
+ The roots, seeded through pad's own =api.ts= (=scripts/bench/client/seed.ts=), so their pads are sealed as a browser seals them:
  + /average/: 186 pads, shaped like the author's own root (=capacity.org=: half under 437 bytes, 90% under 2,992), its root pad 249,000 characters. 2026-10-14: 459,557 characters in all, the root pad 6,097 lines; before, 477,255, the root pad 6,355 lines (this doc said 6,388; the old generator, rerun, gives 6,355).
  + /max/: the quota, 5,000 pads. 2026-10-14: 15,219,960 characters, the root pad 507,903: the most a pad holds (516,095 since sealed pads are padded, 95e4671) less 8 KiB for what the scripts type, its other pads 2,943 each so that the 5,000 fit the root's 16 MiB (=text.ts=). Before: 15.3 MB, the root pad 516,096 characters, which no longer fits a pad.
+ The text, before 2026-10-14, wasn't what the tables say (=text.ts= has the fix):
  + Its generator multiplied past 2^53 in floating point: from its 11,154th draw it repeated a cycle of 10,466, so every root pad was a ~21 KB block over and over, which deflate (Export) collapses far more than it would a person's text.
  + The floors held the generator's first characters, not the seeded pad's text: 6,246 lines where the average root pad had 6,355, and 524,224 characters where the max root pad had 516,096.
  + Every script typed into one seeded database, so later scripts and repeats opened a longer pad than the floor beside them (=costs.ts= found 253,550 characters in the 249,000 one).
  2026-10-14: the floors are the seeded root pad's own text, and each script gets its own server on a fresh copy of the seed (=run-all.sh=).
+ Scripts: =scripts/bench/client/= (=drive.ts= memory, =cpu.ts= CPU, =floor.ts= the bare textarea, =sites.ts= other sites, =typing-profile.ts= where typing's memory goes, =costs.ts= requests and paint, all on =harness.ts='s Chromium and =text.ts='s text). Raw results: =memory-results.jsonl= there (2026-10-11), =results-2026-10-12/= (the night run below) and =results-2026-10-12-evening/= (the evening run, with its =run.sh=), =results-2026-10-12-export/= (Export) and =results-2026-10-14/= (Now, below).
+ The 2026-10-14 run (=run-all.sh=, 06:50–08:04, headless, three runs of each cell) measures the build at 0.2.1 against its floors. The machine was checked idle before it (load 0.36; Zen, Steam and a second Chromium closed; KDE's file indexer suspended); =load.log= has the load every 15 s: at most 1.66 (06:55), its busiest process the benchmark's own Chromium.
+ The 2026-10-12 run (=run-all.sh= as of cf53531, 01:39–02:37, headless only, one run per cell) compares three builds: /old/, the caret as committed (=requestAnimationFrame= every frame); /cheap/, the per-line caret of the working tree forced on, which is what Firefox and Safari ran (since removed, see Typing); /native/, the working tree as is, where Chromium draws the block caret itself (=caret-shape: block=). =load.log= has the load every 15 s: the 1-minute load passed 2 only from 02:18:53 to 02:19:54 (peak 3.56), during /cheap/'s max-root typing, its busiest process the benchmark's own Chromium.
+ Keys are sent as a keyboard sends them (=Input.dispatchKeyEvent=), not =Input.insertText=: 100 characters at the end of the 512 KiB bare textarea took 94.8 s with =insertText=, 5.6 s with key events, spellcheck on or off (=typing-path.ts=). The slow path is CDP's, not Chromium's editing.
+ The 2026-10-12 evening run (21:49–22:14, headless) compares /head/, the last commit, with /now/, the working tree: the poll's ETag and the batch export, the JS caret already gone (Chromium draws its own). Both against copies of one fresh seed, same counts as above. =costs.ts= two runs each, alternating; the near-target cells three runs each on /now/. The 1-minute load stayed at or under 0.92.

+ Fetching and decrypting 16 MB a batch at a time is most of it, +64–71, before any zip: the ≤ 40 target isn't reachable this way. It becomes ≤ 100, which /fix/ met in five runs of six (+100.4 in the sixth); 2026-10-14, three of three (+89.5 to +91.8, Now).
+ /fix/: =loadMany= hands export the decrypted bytes (no string and back), as views of the batch, the zip takes them uncopied, and =crc32= walks them by index. V8's sampled JS allocation over the export: 135.8 → 113.7 MiB, the builtin =next= 28.7 → 8.3 (=crc32='s =for…of=).

+ The browser process holds the finished zip for the download: the runs above downloaded it (=export-pss.ts= didn't refuse downloads until 2026-10-14). Refused, the browser moves +0.0 to +0.2.

* Known costs, from reading the code
Checked against the code (AUDIT.org section 17 has the full list, with what's still to measure):
+ =Pad.svelte:134=: every 5 s the whole pad is downloaded and decrypted, while the tab is visible and nothing is unsaved; the server sends =no-store= and no ETag. Measured: 2.9 MiB a minute on the average root (Requests, above). Fixed (b75f53c): the version is the ETag, 304 while current, and the poll slows to 30 s with the window in the background.
+ =caret.ts:113-129=: a =requestAnimationFrame= loop every frame while a field has focus. Gone with the JS caret.
+ The Argon2 chunk (37 KB, =hash-wasm=) is loaded by the read-only link page, which never derives a password. Fixed (b99defa, Fixes below).
+ =theme.ts:76=: a PNG data URL kept for every colour pair the picker passes through. Fixed (7fd4137): the last two.
+ =[...path]/+page.svelte=: every move between pads unmounted and remounted the editor twice, loading the pad and every name twice (found by the e2e tests). Fixed by 8595472: one list and one pad a move (=costs.ts=). The editor still remounts once per pad (={#key path}=, so nothing typed in one shows in the next), so a move fetched the list again (22,992 bytes on the average root, 613,009 on the max) and the pad, though nothing changed. Fixed (0a7a277, Fixes below): both are asked by version, 304 when unchanged.
