#+TITLE: Encryption and access
#+OPTIONS: ^:{}

The server never sees a password, a key, a pad's text or a subpad's name: a page's address has the path under its root after the =#=, which browsers don't send (=src/lib/href.ts=). The browser does all of it in =src/lib/crypto.ts=; the server's side is =src/lib/server/auth.ts=.

* Keys

#+begin_example
password ─Argon2id(salt)─► master ─HKDF─┬─► auth: proves the password to the server
                                         └─► wrap key: seals the root key
root key (random, one per root) ─HKDF─┬─► content key: AES-GCM over text and names
                                       └─► name key: HMAC of a path, its id in the DB
#+end_example

+ Argon2id at OWASP's minimum: 19 MiB, 2 iterations, 1 lane (hash-wasm). Passwords are NFC-normalised, 8 to 256 characters.
+ Argon2id's cost is kept per root, with its salt (=src/lib/limits.ts=, =ARGON2=): a new password takes today's, and raising it later leaves every root on the one it was claimed with until its next password change. The browser refuses a cost under that floor, or over 256 MiB, 8 iterations or 4 lanes: a server serving a cheaper one would get an =auth= it can guess the password from cheaply, and a dearer one would hang the tab (256 MiB at 8 iterations is about 2 s on the author's laptop). The server refuses the same from a browser.
+ The root key is random and never changes: a password change seals the same key under the new password, so no pad is re-encrypted. It also means a change signs the old password's holders out but doesn't take the key from one who kept it: with a sealed pad from the server or a copy of the database, they can still open it.
+ Every seal is AES-256-GCM with a random 12-byte nonce, bound by its associated data to where it belongs: the root key to its root's name, a pad's text and name to its id. The server can't move a sealed key to another root, or swap two pads' texts or names, without the browser refusing them.
+ The root's theme is sealed under the content key too, bound to =pad theme=.
+ Text, names and a link's copy are padded before sealing (=src/lib/padme.ts=): the plain bytes, a =0x80= marker, then zeros up to the next Padmé size, a length whose binary float has no more mantissa bits than exponent bits (PURBs, [[https://arxiv.org/abs/1806.03160][arXiv 1806.03160]]). At most 12% more, and lengths fall into few sizes; text and links are 256 bytes at least, names 128. Their associated data ends in = padded=; a seal from before padding opens under the old one, and its pad's next save re-seals text and name. The theme isn't padded: it's always the same length. Why these: [[*Padding][Padding]].
+ A pad's id is the base64url HMAC-SHA-256 of its path under the name key: the same path always finds the same row, and the id says nothing about the path.

* What the server keeps

Per root: the salt and Argon2id's cost (public: the gate needs them before the password), SHA-256 of =auth=, the sealed root key and the sealed theme. =auth= carries Argon2id's cost already, so a fast hash is enough. A copy of the database gives an attacker the salts and hashes to guess passwords against at Argon2id's cost, and nothing else. It does show how many pads a root has, and each one's size to its Padmé step: on the author's root, 42 sizes among 180 pads, 12 of them unique. Each pad's kept versions are sealed as the pad is; they add the sizes and save times of up to 10 earlier texts, times the server saw as saves anyway.

* Padding

Powers of two group more for +21%. A name is at most 1,020 bytes; at 128 every name of this root looks the same, for 16 KB more.

* Unlocking

1. The browser derives =auth= and the wrap key, and posts =auth=.
2. The server compares its SHA-256 in constant time. If it matches, it answers with the sealed root key and sets the unlock cookie.
3. The browser opens the root key with the wrap key. If it doesn't open, the server answered for a password its own copy doesn't match, and the browser refuses it.
4. The browser derives the pad keys and keeps them in IndexedDB as non-extractable =CryptoKey=s: a script on the page could use them while it runs, but not read them out. The Content-Security-Policy only lets the app's own scripts run.

The cookie is =__Host-pad=: =HttpOnly=, =Secure=, =SameSite=Lax=, a fresh 256-bit token on every unlock, carrying over the roots the old one had. The database keeps its SHA-256 per root. Unlocks end after 30 days unused or 180 days.

* Wrong passwords

Five are free; after that each doubles the wait, up to 15 minutes. Whose failures count:

+ A browser that has unlocked the root before: only its own. Unlocking sets a second cookie, =__Host-pad-device=, whose token's SHA-256 the database keeps per root; locking leaves it, and 180 days unseen at the root forgets it. So strangers failing the password can't keep out a browser that has been in.
+ Any other: its address's, or for IPv6 its /64's, which one host can have all of.

Nothing is counted per root: anyone could run that up to keep everyone else out. So guesses at one root from many addresses are each slowed per address only, and by the Argon2id every guess costs the guesser.

* Writes from other sites

=SameSite= keeps other sites' requests from carrying the cookie, but other =nassu.online= subdomains are the same site. So every request that changes something must have =Sec-Fetch-Site: same-origin=, or, from a browser too old to send it, an =Origin= matching the page's. Reads are refused with any other =Sec-Fetch-Site= but =none= (the address bar), and pass without one: curl sends none, and a browser too old to send it still has =Cross-Origin-Resource-Policy: same-origin=.

* Read-only links

A link is =/_/<root>/s/<id>#<key>=; its pages within it add =~= and the path under the pad it was made at (=#<key>~a/b=), =~= being outside base64's alphabet. The browser makes both: =id= 16 random bytes, =key= 32. It writes the pad and those under it as JSON, ={"path": …, "pads": [{"path": …, "text": …}], "theme": {"bg": …, "fg": …, "ink": …}}=, deflates it, and seals it under =key= with AES-GCM bound to =id=; and seals =key= under the root's content key, also bound to =id=. The server gets the two sealed blobs and the pad's id, never =key=: it's after the link's =#=, which browsers don't send.

+ Anyone with the link fetches the copy, no cookie needed, and opens it with =key=. Without =key=, =id= gets them nothing they could read.
+ The root's owners list the pad's links, open each =key= with the root's content key, and so can show and copy the links again.
+ Revoking deletes the row. Someone who read the copy before still has what they read.
+ The copy is sealed under its own key, not the root's: a link opens that one copy, nothing else in the root.
+ A link with a password is =#!<key>=, =!= also outside base64's alphabet. Its copy is sealed under HKDF-SHA256 of =key=, salted with Argon2id of the password (salt ="pad share password\n<id>"=, 19 MiB, 2 passes, 1 lane), not under =key=: the link alone doesn't open it, nor the password alone. The cost is fixed, not the root's: the reader has no root to ask. The sealed key the root keeps starts with a byte, 1 for a password, so the owners' copy of the link has its =!=; the server sees the same 61 bytes either way and doesn't learn which links have one. A wrong password after the copy is fetched can be tried again: the page keeps it.
+ The server learns how long a link lasts and whether it opens once: it enforces both (=docs/api/http.org=).
+ Deflating first means the server learns the copy's compressed size rather than its size, to its Padmé step.

* What it doesn't protect against

+ A lost password can't be reset: nothing on the server can open the pads.
