#+TITLE: Installing pad
#+OPTIONS: ^:{}

Pad is one Bun process and one SQLite file, shipped as a Docker image. It needs [[*HTTPS][HTTPS]] in front, and a proxy to put it there: Caddy in the examples, from =deploy/Caddyfile=, pad.nassu.online's.

* Docker

Each release publishes =ghcr.io/nasreddinhodja/pad= for amd64 and arm64, tagged with its version and =latest=: Bun on a distroless base (no shell), running as user 65532, listening on port 5512, with the database in =/data=. With Compose, beside a Caddy on the same host:

#+begin_src yaml
services:
  pad:
    image: ghcr.io/nasreddinhodja/pad:latest
    # Caddy reaches it on 127.0.0.1, and pad sees Caddy's address as the peer.
    network_mode: host
    environment:
      HOST: 127.0.0.1
      PAD_TRUSTED_PROXIES: 127.0.0.1,::1
    volumes:
      - ./data:/data
      - ./backups:/backups
    read_only: true
    cap_drop: [ALL]
    security_opt: [no-new-privileges]
    restart: unless-stopped
#+end_src

Create =./data= and =./backups= before the first start, mode 0700 and owned by 65532; or add =user: '<uid>:<gid>'= with an owner of yours. The image sets =PAD_DB=/data/pad.db= and =BODY_SIZE_LIMIT=1M=; the rest is in [[*Environment variables][Environment variables]]. A =PAD_CONFIG= file goes in with another read-only volume.

=read_only=, =cap_drop= and =no-new-privileges= cost nothing measured, with Docker's default seccomp profile left on. On a laptop (Docker 29.9, 16 threads), the home page from 64 connections at once, three runs of 8 s each:

| Pad run                                          | Requests a second      |
|--------------------------------------------------+------------------------|
| =bun build/index.js= on the host                 | 12,132, 12,039, 12,225 |
| The image, Docker's defaults                     | 12,203, 12,206, 12,374 |
| The image, =read_only=, =cap_drop=, no-new-privs | 12,037, 12,180, 12,274 |
| The same, =seccomp=unconfined=                   | 12,408, 12,498, 12,450 |

Two load clients at once shared the same total (5,976 and 5,964), so the ceiling is pad's one thread, not the client's. With all three set, every end-to-end test passed against the container (=e2e/=, 15), and a backup of a 210 MB database ran (=VACUUM INTO= needs no =/tmp=). Bun exits on =docker stop='s SIGTERM as PID 1 (133 ms, exit 0): no =init= needed. =MemoryDenyWriteExecute= and other W^X switches turn off Bun's JIT: none here.

The same with Podman (not tested here, the flags are the same):

#+begin_src sh
podman run -d --name pad --network host -e HOST=127.0.0.1 -e PAD_TRUSTED_PROXIES=127.0.0.1,::1 \
  --read-only --cap-drop ALL --security-opt no-new-privileges \
  -v ./data:/data:Z -v ./backups:/backups:Z ghcr.io/nasreddinhodja/pad:latest
#+end_src

To build the image yourself: =docker build .= (needs BuildKit, for =$BUILDPLATFORM=).

* Updating

Pull the new image and recreate the container, with a [[*Backups][backup]] first: =docker compose pull && docker compose up -d=. Pinning a version (=:0.1.0=) instead of =latest= makes it a choice.

pad.nassu.online runs =deploy/pad-update= daily from =pad-update.timer=, as root: it takes the latest release's image by digest, runs it only if its attestation says this repo's =release.yml= built it from that tag ([[*Verifying a release][Verifying a release]]), backs the database up, and goes back to the previous image when the new one doesn't answer =/_/limits= within 15 s (kept stopped as =pad-failed=). =pad-update --rollback= goes back by hand. It needs Docker, =curl= and the GitHub CLI, and an =/etc/pad.env= with the host's variables.

* Verifying a release

The image has a signed attestation that this repo's release workflow built it:

#+begin_src sh
gh attestation verify oci://ghcr.io/nasreddinhodja/pad:latest --repo NasreddinHodja/pad.nassu.online
#+end_src

That needs a GitHub login. Each release also attaches the bundle, =image-attestation.json=; with it, gh checks without one (tested with no credentials at all: the release's digest passed, the wrong tag was refused):

#+begin_src sh
gh attestation verify oci://ghcr.io/nasreddinhodja/pad:0.1.0 --bundle image-attestation.json \
  --repo NasreddinHodja/pad.nassu.online --source-ref refs/tags/v0.1.0
#+end_src

Each release also lists the files every page loads, with their hashes (=client-files.sha256=, attested the same way). The same tag builds the same bytes: the release build sets =SOURCE_DATE_EPOCH= to the commit's time (=vite.config.ts=), and a build in the image at =/src= matched one on a laptop's checkout, all 119 files. Anyone can check that an instance serves them:

#+begin_src sh
bun scripts/check-instance.ts https://pad.example.org client-files.sha256
#+end_src

It fetches every listed file and hashes it, and checks every script the home page and a pad's page load is on the list. It caught a chunk with a line added and a page loading a script not in the release. What it can't check: the HTML of each page and its two inline scripts, which the server renders per request (a nonce, the page's data). An operator can change those, and the check passes; it narrows what has to be trusted to them.

* HTTPS

The browser derives keys and encrypts with Web Crypto, which only runs on HTTPS or on =localhost=. Served over plain HTTP from anywhere else, pad's page can't unlock or save anything. Put HTTPS in front, as =deploy/Caddyfile= does.

* Behind a reverse proxy

Tell the server which proxy to believe with =PAD_TRUSTED_PROXIES=, and bind it where only the proxy reaches it (=HOST=127.0.0.1=). From a trusted address, the client is the rightmost =X-Forwarded-For= hop that isn't itself a trusted proxy; from any other, the peer is the client and its =X-Forwarded-For= is ignored (=src/lib/server/address.ts=).

Without =PAD_TRUSTED_PROXIES= behind a proxy, every visitor is the proxy's address: one person's requests use up everyone's 200 a second, one person's new bytes count toward everyone's 1 GiB a day, and wrong passwords from browsers that never unlocked a root back off for all of them. Trusting an address that isn't your proxy lets whoever sends from it pick any address, and a fresh set of meters with it.

adapter-bun's =ADDRESS_HEADER= and =XFF_DEPTH= aren't used: with =ADDRESS_HEADER= set the server refuses to start.

The proxy should also set the headers the app can't put on the files it serves from =static/= and the build: =deploy/Caddyfile= has them. Pages and API answers carry them from the app (=src/hooks.server.ts=).

=deploy/Caddyfile= is pad.nassu.online's, and also sets two of Caddy's defaults tighter. A slow client was held open by Caddy v2.11.7 with its defaults, and cut with these (=deploy/Caddyfile='s global block, measured on the VPS):

| Client                             | Defaults           | =read_header 10s=, =read_body_idle 10s 1024= |
|------------------------------------+--------------------+----------------------------------------------|
| Headers, a byte every 2 s          | still open at 40 s | cut at 12 s                                  |
| A 1 MiB body at 100 bytes a second | still open at 40 s | cut at 22 s                                  |
| A 1 MiB body at 2 KiB a second     | still open at 40 s | still open at 40 s                           |

A body must average 1 KiB a second, so a full save still has 17 minutes. Both are server options, for every site on the same port.

Caddy has no rate limits of its own; the app's hold without one ([[file:../architecture/capacity.org][Capacity and limits]]).

* What the proxy sees

Everything that crosses it, whether it keeps it or not: the client's address, when, the root's name (in page URLs and in every =/_/<root>/…= call), pad ids, read-only link ids, body sizes (a pad's text padded to its Padmé step, plus 28 bytes), when saves happen, the =User-Agent=, and the unlock cookie, which lets whoever holds it read and replace that root's sealed pads until the browser locks, the password changes or it expires. Not a password, a key, a pad's text or a subpad's name: the browser sends the path after the =#= to nobody, and keys and text only sealed. An old address from before that (=/<root>/a/b=) still sends its path once, then redirects.

A proxy that logs keeps that list on disk. Nothing in pad stops an operator from turning a log on; that's what [[file:../architecture/encryption.org][the encryption]] is for.

* Logs

What pad and Caddy write. Both write to standard error; on pad.nassu.online that's journald, which on its Ubuntu keeps it on disk (=/var/log/journal=):

+ Pad: =Listening on …= at start, and a configuration error that stops it. Nothing per request: unmatched paths, wrong methods and malformed bodies wrote nothing (the build, probed with =curl=). An unexpected error prints its stack (SvelteKit's default =handleError=), without the request. At most once an hour, and only if something happened, a line of counts since the last (=src/lib/server/signals.ts=): no address, root or path.
  #+begin_example
  last 60 min: 3 refused (429), 0 failed (5xx), 12 wrong passwords; database 812 MiB of 5120 MiB (16%)
  #+end_example
  Past 90% of =serverBytes= it starts =warning: database nearly full;= and is written every hour there are requests. Refusals are rate limits and backoffs; failures are pad's own errors (a 507 when full among them), not Caddy's 502s. Requests set it off, as they do the purge, so the hour's first request writes the hour before. =docker logs pad= shows it.
+ Caddy, with no =log= directive: no access log. It still logs a request it couldn't serve (=http.log.error=), with the address, the URL and the headers: a 502 while pad restarts does it. =deploy/Caddyfile= turns that logger off (=exclude http.log.error=); after, the same 502 wrote nothing (a throwaway Caddy v2.11.7 on the VPS). Left: start, stop and certificate renewals.

* Floods

The app's limits are per address and per root ([[file:../architecture/capacity.org][Capacity and limits]]): about 10 addresses at their full 200 requests a second fill the VPS. Past that, and past what the machine's link carries, nothing on the machine helps: the provider's network filtering, or a CDN in front, which then sees every request ([[*What the proxy sees][What the proxy sees]]).

* Abuse

A report names a root (its address) or a read-only link. Pad can't read either: a link's text opens with the key after its =#=, so a report that includes the whole link lets the operator open it in a browser and see that copy, and nothing else of the root; a root's pads need its password. =scripts/remove.ts= takes either down at once, with no grace and nothing for the password to bring back. A root goes with its pads, links, unlocks and devices, and its name can be claimed again. A link goes alone:

#+begin_src sh
docker exec pad bun /app/remove.js /data/pad.db root 'https://pad.example/someroot'
docker exec pad bun /app/remove.js /data/pad.db link 'https://pad.example/_/someroot/s/…#…'
#+end_src

It takes an address as the reporter sends it, or a root's name or a link's id, and says what it removed (=removed /someroot: 12 pads, 3 links=), or exits 1 if there's nothing by that name. It runs beside the server, which sees the removal on its next request. Removed rows are zeroed in the file, as the server's own deletions are; copies in [[*Backups][backups]] keep them until those are rotated out. Outside a container: =bun scripts/remove.ts <pad.db> root|link …=, as the user pad runs as. pad.nassu.online's contact is in [[file:../../SECURITY.md][SECURITY.md]].

* Backups

The database is one file, written through a WAL: copying =pad.db= while pad runs can catch it halfway. =scripts/backup.ts= takes a consistent copy with SQLite's =VACUUM INTO= while it runs, checks it with =PRAGMA integrity_check= and keeps the newest seven:

#+begin_src sh
docker exec pad bun /app/backup.ts /data/pad.db /backups 7
#+end_src

The image has it as =/app/backup.ts=; =/backups= is the volume from [[*Docker][Docker]]. On pad.nassu.online, =deploy/pad-backup.timer= runs it daily, and =pad-update= before each switch. Outside a container: =bun scripts/backup.ts <pad.db> <directory> 7=, run as the user pad runs as: opening the database creates its =-wal= and =-shm= files when they're missing, owned by whoever opened it. Copies on the server's own disk survive a mistake, not the disk; pull them elsewhere, e.g. =rsync= from another machine.

A copy is the whole database: root names, salts, the hash the password is checked against, sealed root keys, sealed pads and names, read-only links. Whoever has one can try passwords against it offline, at Argon2's cost per guess. Keep copies as you keep the server. A purge zeroes what it removes from the database, not from copies: a purged pad is in every copy made before it, until that copy is rotated out (after 7 days at one a day).

To restore: stop the container (=docker stop pad=), move =pad.db=, =pad.db-wal= and =pad.db-shm= aside together, put the copy in as =pad.db=, owned by the user pad runs as, and start it.

A drill: keep a root whose password you use nowhere else, with a few pads. On another machine, with this repo, check a pulled copy opens:

#+begin_src sh
bun scripts/check-backup.ts pad-….db <root>   # asks for the root's password
#+end_src

It derives the keys as the browser does and opens every pad's name and text, and the theme. On a copy taken during writes, then served by a fresh pad, it opened all 50 pads; a pad with another pad's bytes failed, as did a wrong password.

* Environment variables

| Variable              | Default         | Description                                                                                                             |
|-----------------------+-----------------+-------------------------------------------------------------------------------------------------------------------------|
| =PAD_DB=              | =data/pad.db=   | The SQLite database; its directory is created if missing                                                                |
| =PAD_CONFIG=          | unset           | A JSON file of limits, see [[*Limits][Limits]]                                                                                    |
| =PAD_TRUSTED_PROXIES= | unset           | Proxy addresses and CIDR ranges, comma-separated, see [[*Behind a reverse proxy][Behind a reverse proxy]]                                          |
| =HOST=                | every interface | Address to listen on (adapter-bun's)                                                                                    |
| =PORT=                | =3000=          | Port to listen on (adapter-bun's)                                                                                       |
| =BODY_SIZE_LIMIT=     | =512K=          | Largest request body (adapter-bun's). Set =1M=: a full pad is =padBytes= padded, plus 28, a link's copy up to 1 MiB              |
| =PROTOCOL_HEADER=     | unset (=https=) | Header naming the request's scheme (adapter-bun's); without it every request is taken as HTTPS                          |
| =HOST_HEADER=         | unset (=Host=)  | Header naming the request's host (adapter-bun's)                                                                        |

The site's origin is the request's =Host= over =https=: adapter-bun has no =ORIGIN= variable (=node_modules/@sveltejs/adapter-bun/src/handler.js=, =get_origin=). The site's name in titles and link previews is that host too.

* Limits

=PAD_CONFIG= names a JSON file whose keys are =GET /_/limits='s; any left out keep their defaults. Sizes in bytes, times in milliseconds. An unknown key, or a value that isn't a number of 0 or more, stops the server on start. Why each default is what it is: [[file:../architecture/capacity.org][Capacity and limits]].

#+begin_src json
{ "serverBytes": 21474836480, "rootBytes": 67108864, "writes": { "perSecond": 2097152 } }
#+end_src

| Key            | Default                        | What it limits                                                                              |
|----------------+--------------------------------+---------------------------------------------------------------------------------------------|
| =padBytes=     | 524288 (512 KiB)               | A pad's text. Past 1,032,191 bytes (padded and sealed, 1 MiB), raise =BODY_SIZE_LIMIT= with it                          |
| =serverBytes=  | 5368709120 (5 GiB)             | The database, past which no pad or link grows                                               |
| =rootBytes=    | 16777216 (16 MiB)              | A root's pads and links                                                                     |
| =rootPads=     | 5000                           | A root's pads, emptied ones included                                                        |
| =linksPerRoot= | 1000                           | Read-only links a root has at once                                                          |
| =writes=       | 16 MiB burst, 1 MiB/s, 16 KiB  | Writes to a root by anyone unlocked there: ={"burst", "perSecond", "floor"}=, in bytes      |
| =open=         | 16 MiB burst, 1 MiB/s, 16 KiB  | Claims, unlocks, locks and link reads, per address                                          |
| =growth=       | 64 MiB burst, 1 GiB a day, 0   | New bytes an address adds to pads and links, across every root                              |
| =requests=     | 5000 burst, 200/s, 1           | Every request an address sends, counted not weighed                                         |
| =backoff=      | 5 free, 900000 (15 min)        | Wrong passwords: ={"free", "maxWait"}=; past =free=, a wait that doubles up to =maxWait=    |
| =grace=        | 2592000000 (30 days)           | How long an emptied pad or a deleted root waits before it's purged                          |
| =retention=    | 0 (never)                      | How long a root may go unused (no unlock, no browser with it open) before it's deleted      |
| =versions=     | 10                             | Earlier texts kept of each pad, the oldest dropped past it; 0 keeps none                    |
| =versionGap=   | 600000 (10 min)                | How old a pad's newest kept text must be before a save keeps the one it overwrites          |

A root =retention= leaves unused is deleted as its owner would delete it, and purged =grace= later: its password brings it back until then. A browser with it open counts as a use at most once an hour; a link's readers don't count. The about page states this server's =retention=. Roots from before the release that brought it count as used on the upgrade.

Kept versions count toward =rootBytes=: a save past it drops the root's oldest versions rather than being refused. A full server (=serverBytes=) keeps none. They go when their pad is purged.

Every request costs its body's bytes, never less than the bucket's =floor=. =burst= and =perSecond= must be more than 0, as must =padBytes=, =serverBytes=, =rootBytes= and =rootPads=.
